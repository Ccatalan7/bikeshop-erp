# Canonical UI Surface Registry

Website Builder work must also follow the mandatory parity, selection,
clipping, routing, media, and save contract in
[`website-editor-contract.md`](website-editor-contract.md).

**Purpose:** prevent business actions from being implemented on an unrouted,
obsolete, or partial UI while the screen employees actually use remains
unchanged.

## Required Rule

A business workflow is not UI-complete until the same shared action is present
on every registered surface where the underlying document can be operated.
Routes, list previews, embedded editors, side panels, quick actions, and mobile
layouts are separate surfaces even when they display the same record.

- Put business behavior in a shared service/widget; surfaces only compose it.
- Do not retain competing `*_old.dart` or unrouted detail/list pages. Git history
  is the archive.
- Before editing UI, trace the real route in `app_router.dart`, its barrel
  export, and every constructor reference with `rg`.
- After editing, verify the employee's normal click path, not only a direct URL
  or isolated widget test.
- Critical workflows require an architecture test that asserts every registered
  surface consumes the shared action and obsolete competitors stay absent.

## Visual and navigation continuity invariant

Every registered composition also follows
[`GUI_DESIGN_PRINCIPLES.md`](../../.github/GUI_DESIGN_PRINCIPLES.md); phone,
tablet, compact, adaptive, and responsive surfaces additionally follow
[`GUI_MOBILE_DESIGN_PRINCIPLES.md`](../../.github/GUI_MOBILE_DESIGN_PRINCIPLES.md).

A row in this registry documents one validated business host. Its table, list,
card, split pane, inline workspace, popover, sheet, modal, or routed
composition is specific to that task and viewport. It is not a template or
visual precedent for another module. Sharing one owner, command, permission,
and persistent effect does not require sharing one container.

When a registered surface opens related work, it preserves the exact origin as
applicable: module, query, filters, scope, tab, selection, disclosures, scroll,
pane state, and draft. Back, close, and cancel return there rather than to a
generic entity list.

Literal colors, radii, shadows, widget classes, and dimensions in historical
specifications are non-authoritative. Registry rows protect capabilities,
ownership, continuity, and validated task-specific composition; the two GUI
guides own current visual direction and how a surface is selected.

`SalesCorrectionsMenu` applies Viñabike's operating policy consistently on the
list preview, routed page, and embedded editor:

- `sent`: an unpaid standalone document may be discarded;
- `confirmed` / `overdue`: an unpaid standalone document may be discarded when
  it has no payment, workshop link, return, or credit note; the atomic command
  records the actor and reason, changes it to cancelled, restores its exact
  stock ledger, archives/reverses its journal evidence, and links the command
  root to the canonical invoice-update trace;
- `paid`: financial credit note and physical customer return.

`Descartar factura` means the sale never happened (test or data-entry error),
not a post-sale customer return. It never physically deletes a posted document.
Cancelled documents remain queryable as audit evidence, but their historical
balance is excluded from `Por cobrar`, overdue counts, and due-date summaries.
The database refuses the command when the source graph is ambiguous instead of
guessing a stock or accounting correction.
Every restored product receives an append-only `sales_invoice_reversal`
movement. The operational movement read model resolves its parent `void`
command so the list labels it `Descarte de factura`, while the detail shows the
invoice, confirmed-to-cancelled transition, actor, mandatory reason, command
operation and trigger-owned stock operation. The original sale movement remains
visible; the pair nets to zero and both stock columns must end synchronized.

Sales invoice confirmation on the list preview, full page, and embedded editor
uses `SalesService.previewNegativeStock`: staff posting is never blocked by a
negative projection, while a compact amber message identifies the affected
products and the database preserves the normal movement/accounting trace.

Public product media ordering is owned by `PublicCommerceProductProjection`.
An optimized URL and its original URL are alternate representations of one
primary image, never separate gallery items. The projection selects the
website-owned primary pair before the catalog fallback pair, emits one preferred
variant, and then appends only distinct gallery media. Product detail, hydrated
JSON-LD, crawler snapshots, Merchant and checkout therefore consume the same
ordered image identity without renderer-only duplicate hiding.

Category collection scope is part of the typed destination contract. The clean
category route has `subtree` semantics and includes products assigned to the
category or any descendant. `category_scope=direct` is the only canonical
direct-membership refinement and passes the singleton category ID to both the
public RPC/facets path and the Edit-mode local projection. The editor must
round-trip that choice visibly as `Categoría y subcategorías` or `Solo productos
asignados a esta categoría`; changing category from the catalog resets to the
inclusive default, while search, brand, price, stock, sort and pagination
preserve the selected scope. Direct-scope URLs are transient
`noindex,follow` with the clean inclusive category route as canonical.

The Website Builder top bar switches workspaces. Only page composition may
show the persistent block inspector; catalog, structure, settings, and
operations use the full workspace while preserving the active page draft.
Category catalog visibility and navigation placement are distinct workflows:
the former controls catalog eligibility, while the latter controls menu links.
The header inspector never writes `header_nav_links`; header/footer links are
`website_navigation` records. Legacy `/website/content` bookmarks redirect to
`/website/destinations` because storefront content is owned by page blocks.
